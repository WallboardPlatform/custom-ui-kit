# AI authoring workflow

For end customers and partners, begin with purpose, actors, read/write operations, customer scope, brand, target surface, and source/deployment ownership. Resolve whether to deliver a standalone site or add a named app to CMS My Apps using a hosted HTTPS URL or uploaded HTML bundle. For CMS delivery, also resolve the app name, selected numeric customer, customer/platform ownership and authorized audience. The builder can use any compatible technology.

For externally hosted components, offer Sites as the default on an OpenAI platform when compatible Sites capabilities are actually available. Ask the user to choose or confirm hosting before provider-specific provisioning or deployment unless already authorized. Continue portable code and local validation while waiting; make the result reviewable before requesting publishing approval. Respect an existing provider, repository, runtime, pipeline, audience or local-only instruction. Hosting choice does not authorize replacing a chosen runtime/database; proceed within an answered choice without repeating the question. A CMS static bundle uses Wallboard hosting and needs no separate frontend provider; an application backend/database still needs its own suitable deployment. See `delivery.hostingChoice` and [hosting requirements](hosting.md).

Use the Wallboard MCP `custom_ui_guide`. Its `guideProvenance` identifies the immutable guide snapshot; `starterSource` selects application source. New projects use current kit `main` unless the user selects a revision. Preserve an existing project's vendored SDK or pin unless an upgrade is requested. Record the selected checkout's actual SHA, read AGENTS.md and relevant docs, install dependencies, and inspect the matching example. Do not check out the guide provenance commit as the default starter.

Before customer API work, call `get_current_user`, obtain contracts through `api_howto`, and resolve customer/branding inputs through ordinary authorized tools. Authoring credentials remain in the builder session. Standalone runtime users sign in through the app's OAuth flow. CMS apps use `createEmbeddedWallboardClient`: the host supplies the ordinary current-user JWT over a private MessagePort, retains refresh credentials and rechecks handoffs. Credentials stay in memory. This trusted frontend retains the user's full normal API authority, including ADMIN authority; selected customer is a request default, and a copied JWT retains normal validity after app closure/removal. See [embedded authentication](authentication.md#embedded-cms-session).

Prefer a browser app when it only calls Wallboard. Add a backend and database for application-owned records, server-side jobs, or credentials. Choose the data ownership/access policy before writing database queries. Confirm consequential runtime writes with the app owner and verify their API contract.

For standalone scaffolding, use `npm run new-app -- <vue|vanilla> <new-directory>` after building the kit. For CMS apps, adapt [the embedded example](../examples/embedded-device-board/README.md) or an existing frontend. `npm run build:embedded` produces a self-contained HTML document and ZIP; the standalone generator has no embedded option. A CMS ZIP requires a regular root `index.html` and relative assets, without a signage CustomApp manifest.

For CMS registration, use `api_howto` with `categories:["customui"]` for the authoritative contract. Customer-owned apps require OWNER+ and the selected numeric customer. ADMIN can instead register platform apps using MCP `customerId:-1` for the explicit platform operation; real customer IDs still determine assignments and runtime selection. Resolve ownership/audience from the user's intent and preserve it: platform global availability defaults to false, and publishing to all customers requires that audience to be explicitly chosen. Normal role/read-only failures remain authoritative.

Create/update metadata and assignments through `api_write`. Read existing metadata before updates and preserve its app ID, immutable source/ownership and unrelated fields. For a bundle, obtain `api_proxy_url` for the exact POST upload path, including the selected customer query for customer-owned apps. Send multipart field `file` with MIME `application/zip` from the execution environment. The existing media upload tools use another contract. Treat the authenticated proxy URL as a credential; do not persist or publish it. Renew it for the proxy's explicit invalid/expired-token error, preserving upstream permission failures. After an uncertain upload failure, read back metadata/revision and resolve the outcome before retrying; never automatically replay a write. Read back metadata and the selected customer's available catalogue, then verify the named My Apps entry and actual launch. Metadata/ZIP upload does not deploy an external host, backend or database.

Confirm the target server has the matching Custom UI API, CMS frontend and storage/proxy isolation deployed. Keep the opaque sandbox; verify provider framing, asset/API CORS, private-port renewal and context/logout/source changes on the actual host. Source builds and synthetic fixtures do not establish deployed availability or provider support. If a deployment gate remains, deliver the reviewable source/artifact and identify it precisely.

Deliver editable source, the exact kit SHA, startup/build commands, configuration placeholders, validation results, and the actual preview/deployed URL or ZIP. When registered, include the stable app ID, source kind, ownership, selected customer and authorized audience. Identify which hosting, login, database durability and iframe behaviors were verified. Keep synthetic fixtures separate from customer data and exclude tokens, authenticated proxy URLs, private customer apps and server registries from source/public handoffs.

The canonical structured contract is [guide/custom-ui-guide.json](../guide/custom-ui-guide.json). The MCP server's sync script snapshots a committed revision into its source tree with provenance; change the contract here rather than maintaining two authored copies.
